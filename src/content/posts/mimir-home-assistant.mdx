i got tired of asking a cloud API to tell me things about my own life.

mimir is a personal AI companion. it runs in WSL on my PC, is accessible from my phone anywhere via tailscale, can control my phone and my PC, and costs me nothing per query. the name is from god of war — [the head in a bag that knows everything](./god-of-war-ragnarok) felt right for a "knows everything but attached to someone else" agent.

## how it's wired

```
phone → tailscale → windows proxy → WSL companion → Hermes (local LLM)
```

longer version:

- my samsung S24 connects to `100.74.240.75:8645` — my PC's tailscale IP
- a python proxy on windows receives that and forwards it to `172.18.122.56:8645` — the companion running in ubuntu WSL
- the companion talks to Hermes, a local LLM server at `127.0.0.1:8642`
- the companion has phone tools (taps, screen reads, app opens) via a shizuku layer in the flutter app
- the companion has PC tools via a windows agent on the other side

why the proxy? WSL2 on my machine has mirrored networking broken — specific to the insider build i'm on. WSL can't bind directly to the tailscale interface, so i wrote a three-line proxy that can. it's ugly but it works and i'll fix it when microsoft fixes it.

## the asyncio bug that killed phone tools

this one took a while.

the companion uses websockets to talk to the phone. phone sends a message → companion streams a response → phone sends back tool results mid-stream (like "here's what's on screen after the tap you asked for").

the bug: the websocket endpoint was sequential. when a chat message came in, it `await stream_session_response(...)` — blocking the receive loop for the entire Hermes run, roughly 40 seconds. so when the phone sent back tool results, they queued up unprocessed until the timeout killed them.

fix: `asyncio.create_task(_handle_chat(...))` instead of `await`. receive loop stays live. tool results land when they're supposed to.

this sounds obvious in retrospect. it always does.

## samsung is adversarial

One UI (samsung's android skin) has a separate battery management layer on top of standard android. "sleeping apps" and "deep sleeping apps" kill websocket connections the moment the app backgrounds. standard battery optimization exemption does nothing — samsung ignores it.

current workaround: keep the flutter app in the foreground if you want tool calls to work. proper fix is FCM integration — how WhatsApp actually stays alive in the background. that's on the list.

the deeper issue is samsung throttles the main dart isolate when backgrounded. `_handlePhoneToolRequest` needs to move to a foreground-service isolate. also on the list.

## what it does today

chat from my phone, get an answer from a local model, zero per-query cost. ask it to do something on my PC or phone, it does it through the tool layer. it knows my context because the context is in the system prompt and the companion persists sessions.

the original premise was doomscroll coaching — mimir watching app usage and intervening. the watcher is half-built; there's a bug where `_currentApp` never clears via the usage-access fallback, so it overcounts screen time. fixing it this week.

north star is ambient: mimir runs all the time, knows who i am, handles the things i used to delegate to stateless APIs that forget me between requests. the LLM is mine. the data stays on my machine. if a provider changes pricing or model behavior, nothing breaks.

the tradeoff is it took a month to make the networking stable. cloud is easier. but easier means someone else controls the stack.
